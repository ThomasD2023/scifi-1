# 写作流程

---

## 一、阶段划分

| 阶段 | 内容 | 交付 | 状态 |
|---|---|---|---|
| **0 · 校准** | 读全部 docs，向用户提交一份"我理解的这本书"（≤800 字），暴露任何理解偏差 | 校准备忘 | ✅ 已通过 |
| **1 · 试笔** | 写卷一第 2 章（韩国栋听证会）作为文体样章 | 一章 | ✅ 已完成（4,051 字符） |
| **2 · 卷一** | 14 章 + 间奏一 | 逐章 | 进行中 |
| **3 · 卷二** | 18 章 + 间奏二（**开工前先做 `docs/14` 全卷槽位普查，裁决 T4**） | 逐章 | |
| **4 · 卷三** | 12 章 + 间奏三 + 终章 + 间奏四 | 逐章 | |
| **5 · 通稿** | 全书连续性核对、数字复算、修辞配额审计 | 修订清单 | |

**为什么第 1 阶段选第 2 章而不是第 1 章**：第 2 章是听证剧 + 技术解释 + 人物出场三合一，是全书最难的文体平衡点。它写对了，后面就稳。

## 二、每章八步循环（不得跳步）

```
01 LOAD      读取资料
02 CHECK     写前检查
03 CONTRACT  章节合同 → 【停下来等用户批准】
04 DRAFT     写初稿
05 REVIEW    读者冷读
06 REVISE    修改问题
07 UPDATE    回写四份文件
08 DECIDE    用户裁决
```

### 01 · LOAD — 读取资料

必读：`CLAUDE.md`｜`00-项目状态.md`｜`docs/07`（含八条通则）｜本章涉及的正典章节｜上一章成稿｜`docs/12` 里本章相关的开放伏笔｜`docs/14` 本章行。

### 02 · CHECK — 写前检查

- 冲突：本章计划与正典、已发生正文有无矛盾；
- 缺失：本章需要而资料没有的设定 → **停，报告，不擅自补全**；
- 时间：查 `08` 轨道日历（已全部算定，直接查）；
- 资源与权限：查 `13`——关键人物有权、有能力这样做吗；
- 数字：逐个对照 `02`，表里没有的用表里公式现算（可跑 python），过程写进合同。

### 03 · CONTRACT — 章节合同

按 `模板/章节合同-实景章.md`（合审文献章与间奏用 `模板/章节合同-文献与间奏章.md`）填写，连同 `14` 中本章行一并冻结。

**⚠️ 提交合同后停下。等用户批准。不要接着写正文。**

**硬闸**：任何一问只能答出"为了推进剧情"，停止，退回细纲。

### 04 · DRAFT — 起草

一次写完整章，不分段交付，不写到一半问"要继续吗"。**按场景写，不把细纲逐条扩句。**落笔前重读 `docs/07`。

### 05 · REVIEW — 读者冷读

逐条过 `workflow/自检清单.md` **A–E 五组**（E 组＝只看正文，不替作者脑补）。问题按 S1/S2/S3 分级列出，每条给证据，不许只写"通过"。

### 06 · REVISE — 修改

**S1、S2 没有清零，不得标记完成。**S3 交稿前尽量清零，残留的列明。

### 07 · UPDATE — 回写（按 `模板/回写清单.md`）

- `docs/08`：轨道日历行／信息状态矩阵／锁定数字／跨文件小改（沿用卷一 2 先例四块）；
- `docs/10`：本章兑现的设定 ⏳ → ✍️；
- `docs/12`：伏笔的埋／推进／回收状态；
- `docs/13`：权限与资源变动（钱、物品、身份、能力、归属）。

### 08 · DECIDE — 用户裁决

这一章好不好看，由用户判断。每写完 5–10 章做一次滚动复盘（保留什么／停止什么／下一阶段试验什么），结果存 `审核与复盘/`。

## 三、跨章一致性守则

1. **数字只有一个出处。**任何时候想写一个数字，先问：它在正典表里吗？不在就现算并写回表里。
2. **光时是硬约束不是修辞。**每写一句跨星球的"他知道了"，先查两地距离，算滞后，确认时间线成立。
3. **人物不许知道他不该知道的。**查信息状态矩阵。
4. **梯度份额只能加不能改。**0.8%、2.1% 一旦写出，全书固定。
5. **卷三的 5.28 AU / 44 分 / 88 分不得改动。**它是全书的收束锚。

## 四、遇到困难时

| 情况 | 做法 |
|---|---|
| 某个情节需要一个物理上不成立的条件 | **改情节，不改物理。**若确实无解，走争议流程 |
| 某章写不动、卡在结构上 | 提交三个不同的场景切法给用户选，不要硬写 |
| 想加一个新设定 | 先证明它是从已有约束**推出来**的，不是贴上去的。做不到就不加 |
| 觉得某个名场面在实际写作中不成立 | 报告用户，给出替代方案。**不要默默略过** |
| 上下文快满了 | 先完成当前章 + 回写台账，再 `/compact`。台账写回是最高优先级 |

## 五、用户偏好（重要）

- **先计划、后执行，计划必须显式批准。**这是硬要求（八步第 03 步的停等即此）。
- 喜欢被指出问题，不喜欢被恭维。**发现设定漏洞要直说，附推导。**
- 喜欢可验算的东西。给数字时附计算过程。
- 反对"为了酷而牺牲严谨"。任何在物理上说不通的漂亮设定，宁可不要。
